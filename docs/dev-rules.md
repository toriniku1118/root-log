# 開発ルール

RootLog の開発の進め方。`CLAUDE.md` の「開発の進め方」の詳細版。人も Claude Code も同じ流れで進める。

## 全体の流れ
要件整理 → 外部設計 → 内部設計 → テスト設計 → issue を作る(または更新する)→ worktree を作る → 実装 → テスト(単体 → 結合 → システム → 受入)→ PR を作る → マージ → ブランチと worktree を削除

## 1. V字プロセス
設計を先に決め、テストは設計の段階と対応させる。

| 設計(左側) | 対応するテスト(右側) | 確認するもの |
|---|---|---|
| 要件整理 | 受入テスト | 要件を満たすか。日々はローカルで確かめ、実機(自分+テスター)は節目だけ(2章)。ステップごとの判断基準(`docs/project/evaluation.md` 5章) |
| 外部設計(画面・遷移・入出力・権限) | システムテスト | アプリ全体で、画面の流れと機能が設計どおりに動く(ウィジェットテスト・統合テスト+ローカル実行での確認手順) |
| 内部設計(構成・データ・処理) | 結合テスト | モジュール同士の連携(画面+保存先、Firebase エミュレーター、権限ルールのテスト) |
| 実装 | 単体テスト | 関数・クラスの動き |

### 各段階で決めること
1. **要件整理**:なぜ必要か、何ができるようになればよいか。要件には `REQ-nnn` の ID をつける。セキュリティ要件(`docs/project/security-requirements.md`)に関わる場合は、どの項目かも書く。
2. **外部設計**:利用者から見た動き。画面(`SCR-nn`)・ワイヤーフレーム・画面遷移・入力と出力・エラーの表示・機能(`FN-nn`)・誰に何が見えるか(権限)。
3. **内部設計**:作り方。アプリの構成(層と責務)・データ・処理の流れ・エラー処理・保存先(メモリ / Firestore)との境目。
4. **テスト設計**:単体・結合・システム・受入の4段階それぞれで、何をどう確認するか。どの REQ をどのテストで確かめるか。

### 設計書の置き場所(初版は #22 で作成)
| 文書 | 内容 |
|---|---|
| `docs/spec/requirements.md` | 要件一覧(`REQ-nnn`)、優先度、状態 |
| `docs/spec/external-design.md` | 画面一覧(`SCR-nn`)、ワイヤーフレーム、画面遷移、機能一覧(`FN-nn`)、権限 |
| `docs/spec/internal-design.md` | 構成、データモデル、状態管理、保存先の差し替え、エラー処理 |
| `docs/spec/test-plan.md` | 4段階のテスト観点と実行コマンド、REQ → 設計 → テストの対応表 |

- ID は連番。欠番は再利用しない。廃止した ID は「廃止」と残す。
- 1つの開発項目(issue)では、関係する REQ・SCR・FN の ID を issue に書き、詳しい内容は設計書に書く。
- **設計を変えるときは、先に設計書を直す**。設計書の更新は、実装と同じ PR に含める。
- 決まっていないことがあれば、作業を止めて先に決める(ユーザーに確認する)。設計が途中で変わったら、設計書と issue を更新してから実装を直す。
- 小さな変更(誤字の修正など)は、issue に「設計書への影響なし」と書けば、設計の更新を省いてよい。ただし issue・worktree・PR は省かない。

## 2. ローカル優先(実機は節目だけ)
日々の確認は、ローカル(開発PC)で行う。実機は、デバッグ版の転送だけで10分ほどかかるため、必要なときに絞る。

**ローカルでの確認**
- `flutter test`:ウィジェットテスト・統合テスト。画面の表示・操作・遷移を、画面を出さずに確かめる。
- ローカル実行:Flutter の Web サーバー(`flutter run -d web-server`)で画面を動かして見る(Windows のブラウザから操作でき、ホットリロードもできる)。環境の整備は別の issue で行う。整うまでは、自動テストで確かめる。
- Firebase:ローカルのエミュレーター(`docker compose up firebase`)を使う。開発用・本番用の Firebase プロジェクトへの接続は、ローカルで機能が一通り動いてから。

**実機で確認するとき**(これ以外は、実機なしでマージしてよい)
- 端末に依存する機能:カメラ、写真の撮影時刻(EXIF)、通知、Apple / Google のサインイン
- ステップの節目(ステップを完了する前)
- テスター配布の前
- 手順は `docs/android-device-wsl2.md`。

ローカル(Web など)で確かめた場合は、端末固有の動きをまだ確かめていないことを、PR に書く。

## 3. ワイヤーフレーム方針(機能を優先する)
- 画面は Material の標準部品だけで作る。色・余白・アイコン・アニメーションなど、見た目の作り込みはしない(テーマは既定のまま)。
- 1画面を作り込む前に、全画面の機能を一通りつなぐ。機能の優先順は、`docs/spec/requirements.md` の優先度に従う。
- 外部設計のワイヤーフレームは、Markdown の文字図で書く(差分が見えて、リポジトリで管理できる)。
- 見た目のデザイン(配色・レイアウト・アイコンなど)は、機能がそろったあとの別の作業とする。
- ワイヤーフレームでも省かないもの:入力の検証、エラーの表示、権限(非公開が初期値)、日本語表示、テスト。

## 4. issue と sub-issue
- 開発項目は必ず issue にする。issue がない作業はしない。
- issue の本文は、テンプレート(`.github/ISSUE_TEMPLATE/dev-item.md`)に沿って、要件(REQ の ID)・外部設計・内部設計・テスト設計・完了の条件・セキュリティへの影響を書く。
- 大きい項目は親 issue にして、画面ごと・機能ごとなどに分けた sub-issue をぶら下げる。
  - 親 issue:目的と全体の完了条件を書く。
  - sub-issue:1つが「1つの PR で終わる大きさ」になるように分ける。
- sub-issue は GitHub の sub-issue 機能で親に紐づける(紐づけできない場合は、親 issue の本文にチェックリストで `- [ ] #番号` と書く)。
- ラベルの目安:`step1` 〜 `step6`(開発ステップ)、`security`、`docs`、`bug`。

## 5. worktree とブランチ
- 作業は必ず worktree で行う。`main` の作業ディレクトリでは編集しない。
- worktree は `.claude/worktrees/` 以下に作る(Git に含めない)。
- ブランチ名:`<種類>/<issue番号>-<英数字の短い説明>` 例)`feat/12-plant-list`、`docs/3-dev-rules`。種類は `feat` / `fix` / `docs` / `chore`。
- 1つの worktree・ブランチ・PR は、1つの issue(または sub-issue)に対応させる。
- Docker は、どの worktree からでも同じイメージ・キャッシュ・adb の認証キーを使う(`docker-compose.yml` で `name: rootlog` に固定)。ただし `node_modules` も共有されるので、ブランチで `package-lock.json` が変わったら `npm ci` で合わせる。
- 作業が終わった worktree に、ディレクトリ名付きの Docker イメージやボリュームが残っていたら削除する。

## 6. PR とマージ
- PR の本文に、`Closes #issue番号`、変更の概要、設計書の更新、各段階のテスト結果を書く(テンプレート:`.github/pull_request_template.md`)。
- **マージの承認は不要**。次を確認できたら、自分でマージしてよい。
  - 設計書を更新した(または「影響なし」と issue に書いてある)。
  - 該当する段階のテスト(単体・結合・システム)が全件合格している。ローカルで確かめた項目は、その方法と結果を書く。実機での確認が必要な項目(2章)は、実機で確かめた結果を書く。
  - `firebase/` を変えた場合:`npm test` と型チェックが全件合格している。
  - 権限ルールを変えた場合:「見えてはいけないものが見えない」テストを追加してある。
  - 秘密情報(APIキー・秘密鍵・`google-services.json`・`GoogleService-Info.plist`)が含まれていない。
- マージ方法は squash マージ(`gh pr merge --squash --delete-branch`)。履歴を1 issue = 1 コミットにそろえる。
- 確認で失敗した場合はマージせず、直してから再確認する。

## 7. マージ後の片付け
- リモートのブランチを削除する(`--delete-branch`)。GitHub のリポジトリ設定「Automatically delete head branches」も有効にしておく。
- ローカルのブランチと worktree を削除する(`git worktree remove <パス>` と `git branch -D <ブランチ>`。squash マージ後は `-d` が使えないため)。
- `main` を最新にする(`git pull`)。
- issue が閉じていることを確認する。sub-issue がすべて閉じたら、親 issue も閉じる。

## 使うコマンドの例
```bash
gh issue create --title "..." --body-file issue.md
gh issue develop <番号> --name <ブランチ名>          # 任意。ブランチ名を issue に紐づける
git worktree add .claude/worktrees/<名前> -b <ブランチ名> origin/main
gh pr create --title "..." --body "Closes #<番号> ..."
gh pr merge --squash --delete-branch
git worktree remove .claude/worktrees/<名前> && git branch -D <ブランチ名>
```
